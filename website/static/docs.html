Document Scope: This manual provides a complete technical reference for the NUCLEO-F446RE embedded ECU system including all firmware interfaces, hardware connections, OTA update protocol, and web dashboard API endpoints. It is intended for firmware engineers, systems integrators, and QA personnel working with this platform.

1System Overview

The NUCLEO-F446RE ECU is an embedded control unit built around the STM32F446RET6 microcontroller (ARM Cortex-M4, 180 MHz, 512 KB Flash, 128 KB SRAM). It exposes two independent command channels — a wired USB/UART channel and a wireless WiFi channel — both controlled from a centralized web dashboard running on a host PC.

Wire Channel (UART2)

  • Physical: PA2/PA3 via ST-LINK USB bridge
  • Host: COM5 at 115200 baud, 8-N-1
  • Direct byte commands from Flask server
  • Response bytes returned over same UART
  • Supports: LED, BTLD, RUN_TIME, VERSION

WiFi Channel (ESP8266 → UART1)

  • Physical: PA9/PA10 (UART1) ↔ ESP8266
  • ESP hosts HTTP server on port 80
  • Flask POSTs to http://{esp_ip}/cmd
  • ESP forwards bytes to STM32 over UART1
  • ESP also acts as autonomous OTA agent

Web Dashboard

  • Python Flask + SocketIO, port 5000
  • Real-time push via WebSocket events
  • Drag-and-drop firmware upload (.bin)
  • COM port selector and baud config
  • Channel selector: Wire / WiFi / Both

Key Features

  • OTA firmware update via ESP8266 downloader
  • Hardware bootloader trigger (PC3 pin)
  • IWDG watchdog with RTOS-refreshed pet
  • RTC runtime reporting over UART2
  • ADC: LDR (PA0) and internal temperature

3Command Byte Protocol

All control messages are single-byte commands transmitted over UART. The STM32 firmware decodes each byte in the ISR (interrupt service routine) for the respective UART peripheral. The ESP8266 intercepts certain bytes (particularly 0x04) before forwarding others to the MCU.

Protocol Detail: All UARTs are configured at 115200 baud, 8-N-1 (8 data bits, no parity, 1 stop bit). Commands are single bytes with no framing or checksum; responses are variable-length strings terminated with \r\n, except for version queries which are null-terminated strings.

3.1 Command Byte Reference Table

Byte Command Name Wire (UART2) WiFi (UART1) Description
0x01 led_on ✓ Supported ✓ Supported Drive PA5 HIGH — turns on on-board LD2 LED
0x02 led_off ✓ Supported ✓ Supported Drive PA5 LOW — turns off on-board LD2 LED
0x03 btld_jump ✓ Supported ✓ Supported Configure PC3 as output and drive LOW — asserts bootloader select signal
0x04 btld_update ✓ UART2 → STM32 ▶ ESP handles directly Wire path: STM32 writes 0x04 to UART1 → signals ESP to start OTA.
WiFi path: ESP intercepts in /cmd handler and triggers OTA immediately without forwarding to MCU.
0x05 run_time ✓ Supported ✓ Supported Read current RTC value and transmit formatted time string over UART2
0xA1 get_version ✓ Supported ✓ Supported Reply with the FIRMWARE_VERSION string constant over the receiving UART. WiFi path: response is also forwarded to UART1 so ESP can read the version during OTA.
Note on 0x04 asymmetry: When the wire channel sends 0x04, the STM32 receives it on UART2 and then re-emits 0x04 on UART1 toward the ESP. The ESP's UART1 listener then interprets it as an OTA trigger. When the WiFi channel sends 0x04, the Flask server POSTs it to the ESP's HTTP /cmd endpoint, and the ESP handles it directly — the STM32 is not involved in this path.

Response Format

Command Response Example Notes
0x01 / 0x02 (no response) State change only; no ACK byte
0x03 (no response) PC3 asserted; system may reset
0x04 (no response to host) STM32 → ESP OTA trigger forwarded internally
0x05 RTC: 14:32:07\r\n HH:MM:SS format
0xA1 FW:v1.2.3\0 Null-terminated version string

UART1 vs UART2 ISR Symmetry: Both ISRs call the same process_command(uint8_t byte, UART_HandleTypeDef *huart) function with the receiving UART handle as context. The only asymmetry is that UART2 accepts 0x04 (BTLD_UPDATE) while UART1 ignores it (since 0x04 arriving on UART1 comes from the ESP and would be circular).

8OTA Firmware Update Flow

The OTA (Over-The-Air) update mechanism allows the STM32 firmware to be updated wirelessly without physical access to the board. The process is fully automated once a new firmware binary is uploaded to the server.

  1. Upload: User drags and drops a .bin firmware file onto the web dashboard. The browser POSTs it to /upload with the version string.
  2. Server stores: Flask saves the binary to uploads/firmware.bin and writes the version string to uploads/version.txt. Responds with {ok, version, size}.
  3. ESP polls version: Every 30 seconds the ESP issues HTTP GET to /version. Alternatively, if the user clicks "Trigger Update" or sends command 0x04, the poll is forced immediately.
  4. Query STM32 version: ESP sends 0xA1 byte over UART1. STM32 responds with its compiled-in FIRMWARE_VERSION string. ESP reads the response with a 1-second timeout.
  5. Version comparison: If server version equals STM32 version (and not forced), no update is needed and the ESP returns to idle. If versions differ, or the update was force-triggered, OTA proceeds.
  6. Download: ESP calls Serial.end() to pause UART, then issues HTTP GET to /firmware, buffering the binary in RAM. Serial.begin(115200) resumes after download.
  7. Reset into bootloader: ESP pulses the NRST pin (D1) LOW for 100 ms → STM32 hardware-resets. The BTLD_SEL line (PC3) must be asserted LOW before reset so the STM32 ROM bootloader starts instead of the application.
  8. Flash transfer: ESP sends the 0x55 UART bootloader sync byte, then streams raw firmware bytes over UART1 at 115200 baud. The STM32 ROM bootloader receives these, erases flash pages, and programs new firmware.
  9. Verify: ESP waits 2 seconds for STM32 to soft-reset into the new application, then sends 0xA1 again and compares the version reply to the expected new version.
  10. Notify: ESP POSTs result to /status with {version, status: "success"|"failed"}. Flask emits a flash_result SocketIO event. The dashboard displays a toast notification with the outcome.

9RTOS Task Schedule

The STM32 firmware runs a lightweight cooperative/preemptive RTOS scheduler. Tasks are registered with fixed periods and dispatched by the OS tick timer. The watchdog refresh task is critical — if it misses its deadline, the IWDG fires a hardware reset.

Task Name Period Priority Function Called Description
OS_5ms_Task 5 ms High (reserved) Reserved for future high-frequency control tasks (e.g., PID loop, ADC sampling)
OS_10ms_Task 10 ms High LED() Applies the LED_Global variable to PA5 output. This decouples ISR command processing from GPIO state updates.
OS_20ms_Task 20 ms Medium (reserved) Reserved for future periodic tasks (e.g., sensor reads, PWM updates)
OS_50ms_Task 50 ms Medium (reserved) Reserved for future lower-frequency tasks (e.g., UART telemetry, display update)
OS_100ms_Task 100 ms Low IWDG_Refresh() Writes the IWDG key register (KR = 0xAAAA) to reset the watchdog counter. IWDG is configured with a timeout greater than 100 ms so any missed refresh causes reset.
Watchdog Configuration: The IWDG (Independent Watchdog) uses the LSI oscillator (~32 kHz) with a prescaler of /256 and a reload value that gives a timeout of approximately 800 ms. Since the RTOS refreshes every 100 ms, the system has ~8x margin before a reset. If any task blocks or the scheduler stalls, the watchdog fires within 800 ms.

RTOS Tick Architecture

  SysTick_Handler (every 1 ms)
        │
        ├── OS_tick_counter++
        │
        ├── if (tick % 5   == 0) ──► schedule OS_5ms_Task
        ├── if (tick % 10  == 0) ──► schedule OS_10ms_Task  →  LED()
        ├── if (tick % 20  == 0) ──► schedule OS_20ms_Task
        ├── if (tick % 50  == 0) ──► schedule OS_50ms_Task
        └── if (tick % 100 == 0) ──► schedule OS_100ms_Task →  IWDG_Refresh()

  Main Loop
        │
        └── OS_Dispatch() ──► run any pending tasks in priority order
                          ──► UART ISRs can preempt (NVIC priority < SysTick)

System Timing Summary

STM32F446RE Clocks

  • SYSCLK: 180 MHz (PLL from HSE/HSI)
  • AHB: 180 MHz
  • APB1: 45 MHz (UART2, TIM3)
  • APB2: 90 MHz (UART1)
  • LSI: ~32 kHz (IWDG, RTC)

Communication Timing

  • UART1/2 baud: 115200 bps
  • Byte transfer time: ~87 µs
  • ESP OTA poll: every 30 s
  • ESP IP register: every 2 min
  • ESP /cmd HTTP timeout: 2 s
